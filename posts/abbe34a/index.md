## 1. 手册使用说明

### 1.1 适用读者

本手册面向企业 IT 管理员与运维人员，聚焦日常网络故障排查中最常用的 Windows 内置命令，覆盖从单点连通性测试、全网段设备清点、故障返回信息解读到 TCP 连接状态分析的完整链路。全部命令均为系统自带，不依赖任何第三方工具，可直接在生产环境中使用。既有可即查即用的速查表，也有逐参数的深度注释，新手可按顺序阅读，老手可按目录直达目标章节。

### 1.2 系统适用性标注约定

手册中所有命令均按以下图例标注适用性，便于在混合系统环境中快速判断：

| 图例                | 含义                                                      |
| ------------------- | --------------------------------------------------------- |
| ✅ 全版本通用        | Windows XP → Windows 10/11 及对应 Server 系列均可直接使用 |
| ⚠️ 受限/注意         | 需要管理员权限、需启用可选功能，或在新系统中有更优替代    |
| ❌ 旧系统专属/已过时 | Win10/11 上已废弃、无实际效果或官方不再推荐               |

版本基准说明：以 **Windows 10（22H2）/ Windows 11** 为"新系统"基准；凡在该环境下行为有变化、需要额外配置或已有官方 PowerShell 替代的命令，均在正文中以 ⚠️/❌ 标注，并在第 9 章汇总对照。

### 1.3 运行环境与权限建议

- 打开普通 CMD：`Win + R` → 输入 `cmd` 回车；打开管理员终端：`Win + X` → 「终端(管理员)」或右键开始菜单。
- **无需管理员权限**的命令：`ping`、`arp -a`、`ipconfig`、`tracert`、`pathping`、`netstat`、`nslookup`、`getmac`、`route print`。
- **需要管理员权限**的操作：`arp -d` / `arp -s`、`route add/delete/change`、`netsh winsock reset` 等修复类命令、`netstat -b`。
- 快速检测当前窗口是否具有管理员权限：执行 `net session`，正常返回会话列表即为管理员，报「拒绝访问」则为普通权限。
- Windows 10/11 默认内置 Windows PowerShell 5.1，第 9 章的替代命令均以其为基准；PowerShell 7 需另行安装，文中单独标注。

### 1.4 命令注释约定

- 正文命令保持**可直接复制执行**。CMD 的注释符是 `REM` / `::`，且无法出现在命令行中间，因此交互式单行命令的参数注释统一用「参数详解表」呈现，不在命令中夹杂无效字符。
- `.bat` 批处理脚本内使用 `::` 注释（批处理内合法语法，可直接保存运行）。
- PowerShell 代码块内使用 `#` 注释。
- 文中示例 IP 统一使用 `192.168.1.0/24` 网段，请按实际环境替换网段前缀。

## 3. Ping 命令详解

### 3.1 作用与语法

Ping 基于 ICMP 协议的回显请求（Echo Request）/回显应答（Echo Reply）机制工作：本机向目标发送请求报文，目标返回应答报文，据此判断目标是否可达、链路延迟多少、中间经过几台路由器。它是网络排查的第一入口——先确认 IP 层是否通畅，再考虑端口、服务、权限等上层问题。

```bat
ping [-t] [-a] [-n count] [-l size] [-f] [-i TTL] [-r count] [-s count] [-w timeout] [-S srcaddr] [-4|-6] 目标地址
```

### 3.2 参数详解表

| 参数               | 作用                                                 | 默认值/范围                | 适用系统 | 典型场景                                               |
| ------------------ | ---------------------------------------------------- | -------------------------- | :------: | ------------------------------------------------------ |
| （无参数）         | 发送 4 个 32 字节回显请求并等待应答                  | 4 次 / 32 字节 / 等 4000ms |    ✅     | 单点连通性快速验证                                     |
| `-t`               | 持续 ping 直到按 `Ctrl+C` 停止，停止时输出统计       | —                          |    ✅     | 长时间监控丢包率变化、稳定性观测                       |
| `-a`               | 将目标 IP 反向解析为主机名（DNS/NetBIOS）            | —                          |    ✅     | 判断 IP 对应设备；辅助区分「防火墙拦截」与「确实离线」 |
| `-n count`         | 指定发送回显请求的次数                               | 默认 4                     |    ✅     | 批量扫描时设 `-n 1` 提速                               |
| `-l size`          | 指定发送缓冲区（数据包）大小，单位字节               | 默认 32，最大 65500        |    ✅     | 大包测试；配合 `-f` 排查 MTU 问题                      |
| `-f`               | 设置「不分段」（DF）标志，禁止途中路由器分片         | —                          |    ✅     | 与 `-l` 配合定位路径最小 MTU                           |
| `-i TTL`           | 指定发出报文的生存时间（TTL 初值）                   | 128（Windows）             |    ✅     | 受控跳数测试                                           |
| `-r count`         | 记录去程经过的 count 个路由器（1–9）                 | —                          |    ✅     | 短路径（≤9 跳）查看实际走向                            |
| `-s count`         | 指定 count 个跳的时间戳（1–4）                       | —                          |    ✅     | 少用，粗测分段时延                                     |
| `-w timeout`       | 等待每次应答的超时毫秒数                             | 默认 4000                  |    ✅     | 内网扫描设 200–500，大幅缩短等待                       |
| `-S srcaddr`       | 强制使用指定源地址发送（**区分大小写，必须大写 S**） | 自动选择出口               | ✅ Vista+ | 多网卡服务器指定从哪个 IP 发起                         |
| `-R`               | 使用路由标头同时测试反向路由（仅 IPv6）              | —                          | ✅ Vista+ | IPv6 双向路径验证                                      |
| `-c comp`          | 指定路由隔离区编号（Hyper-V 网络虚拟化）             | —                          | ✅ Win10+ | HNV 虚拟化环境专用，桌面环境极少用                     |
| `-p`               | ping Hyper-V 网络虚拟化提供程序地址                  | —                          | ✅ Win10+ | HNV 环境专用                                           |
| `-4`               | 强制使用 IPv4                                        | 自动                       | ✅ Vista+ | 域名同时解析出 v6/v4 时指定 v4                         |
| `-6`               | 强制使用 IPv6                                        | 自动                       | ✅ Vista+ | IPv6 连通性测试                                        |
| `-v TOS`           | 指定服务类型字段                                     | —                          |    ❌     | 现代设备普遍忽略该字段，已无实用价值                   |
| `-j / -k hostlist` | 宽松/严格源路由                                      | —                          |    ❌     | 沿途设备普遍禁用源路由，实际不可用                     |

> 提示：理解每个参数的「代价」比死记命令更重要——`-w 4000` 默认超时是单点测试的可靠性设计，套用到批量扫描就是灾难（一次 254 地址的扫描可能超过 8 分钟），见 §4.1。

### 3.3 六种诊断目标：各自在测什么

| 目标                    | 诊断意义                                                     | 不通时说明                                                   | 示例                                    |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | --------------------------------------- |
| `ping 127.0.0.1`        | 回环测试：报文不经过网卡与网线，直接交给本机 IP 协议软件，验证 TCP/IP 协议栈安装与运行是否正常 | 协议栈损坏/驱动异常 → 尝试 `netsh winsock reset` 后重启      | `ping -n 4 127.0.0.1`                   |
| `ping localhost`        | localhost 是网络保留名、127.0.0.1 的别名；能解析应答说明名称机制正常 | 不通说明 hosts 文件异常（`C:\Windows\System32\drivers\etc\hosts`） | `ping -n 2 localhost`                   |
| `ping 本机 IP`          | 报文经过本机网卡，验证网卡硬件/驱动与 IP 配置                | 网卡被禁用、驱动故障、IP 配置错误                            | `ping 192.168.1.10`                     |
| `ping 局域网其他 IP`    | 报文经网卡与网线到达对端再返回，验证同网段链路               | 0 应答 → 子网掩码错误/网卡配置错误/网线故障；若沿途有路由器，先 ping 本网段路由器接口 IP，再 ping 对端网段路由器接口 IP，逐段定位 | `ping 192.168.1.20`                     |
| `ping 网关`（补充）     | 验证内网出口设备可达，是「上不了网」排查的分水岭             | 内网链路或网关问题                                           | `ping 192.168.1.1`                      |
| `ping 远程地址`（补充） | 验证出口与互联网连通性；用 IP 与域名各测一次可分离「路由问题」与「DNS 问题」 | IP 通、域名不通 → DNS 故障                                   | `ping 223.5.5.5` / `ping www.baidu.com` |

### 3.4 网络突然中断：四步自诊断法

按由近及远的顺序逐步缩小故障范围，每一步失败即锁定问题域：

以下示例按顺序执行（IP 请按实际环境替换，对应上表第 1–4 步）：

```bat
ping 127.0.0.1
ping 192.168.1.10
ping 192.168.1.1
ping 223.5.5.5
ping www.baidu.com
```

| 卡在哪一步               | 问题域            | 处理方向                              |
| ------------------------ | ----------------- | ------------------------------------- |
| 第 1 步失败              | 本机协议栈        | `netsh winsock reset` → 重启          |
| 第 2 步失败              | 网卡/驱动/IP 配置 | 启用网卡、重装驱动、`ipconfig /renew` |
| 第 3 步失败              | 网线/交换机/网关  | 换网线换端口、核对网关地址            |
| 第 4 步失败（IP 也不通） | 上联线路/出口设备 | 联系运营商/网络组                     |
| 第 4 步 IP 通、域名不通  | DNS               | `ipconfig /flushdns`，或改用公共 DNS  |

## 4. 网段批量扫描实战

### 4.1 为什么要扫整个网段

在没有网管系统、也没有 DHCP 地址列表查看权限的环境里，批量 ICMP 探测是最朴素也最有效的设备清点手段：把目标从「一台主机」扩展成「一个地址段」，一次性摸清哪些 IP 在线、哪些空置、哪些延迟异常。局域网内该操作基本无副作用，且完全不需要第三方工具。

**耗时是唯一需要管理的问题**。Windows ping 默认发 4 个包、每个等待 4000ms，这套默认值是给单点测试设计的；套用到 /24 网段（254 个地址）：

| 参数组合              | 耗时估算（约半数地址为空） | 结论                |
| --------------------- | -------------------------- | ------------------- |
| 默认参数              | ≈ 127 × 4s ≈ 8.5 分钟以上  | 不可接受            |
| `-n 1 -w 200`（串行） | ≈ 254 × 0.2s ≈ 51 秒       | 日常可用            |
| `-n 1 -w 200` + 并行  | 数秒至十几秒               | 大网段/多网段时使用 |

核心口诀：**单包探测（`-n 1`）+ 短超时（`-w 200`）**——批量扫描只需确认「活没活」，不需要发几十个包。

### 4.2 for /L 循环语法拆解

CMD 中做批量操作绕不开 `for` 循环，标准写法：

```bat
for /L %i in (1,1,254) do ping -n 1 -w 200 192.168.1.%i
```

| 片段        | 含义                                                         |
| ----------- | ------------------------------------------------------------ |
| `for /L`    | 以数字递增方式循环（/L = List of numbers）                   |
| `%i`        | 循环变量。**CMD 窗口手打用单 `%i`；写入 .bat 文件必须用 `%%i`**（详见 §4.8） |
| `(1,1,254)` | 三个数字 = (起始值, 步长, 结束值)：从 1 开始，每次加 1，数到 254 |
| `do`        | 后接每次循环实际执行的命令                                   |

执行后屏幕飞速滚动 254 次 ping 结果，此时还看不出谁在线谁离线——需要配合过滤。

### 4.3 过滤输出：只看存活主机

成功应答的行包含 `TTL=` 字样，超时行则是「请求超时」「无法访问目标主机」。用管道 + `findstr` 只保留关键行：

```bat
for /L %i in (1,1,254) do @ping -n 1 -w 200 192.168.1.%i | findstr "TTL="
```

| 片段             | 含义                                               |
| ---------------- | -------------------------------------------------- |
| `\|`             | 管道符：把前面命令的输出交给后面命令处理           |
| `findstr "TTL="` | 仅保留包含 `TTL=` 的行（即 ping 通的地址及其延迟） |
| `@`              | 抑制回显：不显示命令本身只显示结果，滚屏更干净     |

**反向过滤**——只看没有响应的地址（排查「谁掉线了」）：

```bat
for /L %i in (1,1,254) do @ping -n 1 -w 200 192.168.1.%i | findstr /V "TTL="
```

`/V` 表示取反，输出不含 `TTL=` 的所有行（含「请求超时」「无法访问目标主机」「一般故障」等）。⚠️ 注意：反向筛选结果只能说明「该 IP 未正常响应 ping」，**不能直接断定设备离线**——设备可能只是禁用了 ICMP（见 §5.1、§8 场景三）。

### 4.4 结果导出到文件

扫描结果落盘保存，避免「看完就没」：

```bat
for /L %i in (1,1,254) do @ping -n 1 -w 200 192.168.1.%i | findstr "TTL=" >> ping_result.txt
```

| 片段 | 含义                                                         |
| ---- | ------------------------------------------------------------ |
| `>>` | 追加写入：每次结果接在文件末尾                               |
| `>`  | 覆盖写入：⚠️ 循环中误用 `>` 会导致每次清空重写，最终文件只剩最后一行——这是最常见的翻车点 |

扫完用 `type ping_result.txt` 查看或记事本打开；需要规整数据（仅 IP + 延迟）时，CMD 文本处理较笨拙，直接粘贴到 Excel 分列更高效。

### 4.5 不同网段与多网段扫描

网段变了，公式不变——只替换 IP 前缀（常见内网段：192.168.0.0/24、10.0.0.0/24、172.16.0.0/24）：

```bat
for /L %i in (1,1,254) do @ping -n 1 -w 200 192.168.0.%i | findstr "TTL="
for /L %i in (1,1,254) do @ping -n 1 -w 200 10.0.0.%i | findstr "TTL="
```

跨多个子网段（如 10.10.0.1 – 10.10.5.254 共 6 个 /24）用嵌套双循环，外层遍历第三段、内层扫描主机位：

```bat
for /L %j in (0,1,5) do for /L %i in (1,1,254) do @ping -n 1 -w 200 10.10.%j.%i | findstr "TTL="
```

> ⚠️ 嵌套循环耗时长且影响面大，动手前先确认目标网段范围，不要漫无目的地扫。

### 4.6 并行提速：start /b

串行循环的瓶颈是「每个 ping 要等结果（或超时）才开始下一个」。`start /b` 可让 ping 在后台并行执行：

```bat
for /L %i in (1,1,254) do @start /b ping -n 1 -w 200 192.168.1.%i | findstr "TTL="
```

⚠️ 坑：`start /b` 与管道符配合时输出重定向行为不可控，结果可能乱序或丢失。更稳妥的并行方案是让每条 ping 靠**退出码**判断成败，成功才写入清单文件：

```bat
for /L %i in (1,1,254) do @start /b cmd /c "ping -n 1 -w 200 192.168.1.%i >nul 2>&1 && echo 192.168.1.%i >> alive.txt"
```

| 片段                    | 含义                                                 |
| ----------------------- | ---------------------------------------------------- |
| `cmd /c "..."`          | 起一个子 CMD 执行引号内的完整命令串（并行单元）      |
| `>nul`                  | 丢弃 ping 的正常输出（屏幕不滚屏）                   |
| `2>&1`                  | 把错误输出合并到标准输出一并丢弃                     |
| `&&`                    | 仅当前一条命令**退出码为 0（成功）**时才执行后续命令 |
| `echo ... >> alive.txt` | 把存活 IP 追加到清单文件                             |

经验法则：单个 /24 用串行（`-w 200` 下约 1 分钟）足够；跨多段扫描再启用并行，避免临时文件高并发写入的 IO 竞争。

### 4.7 批处理脚本完整版（双击即用）

把功能封装为 `.bat`，规避手敲错误与单双百分号问题，注释已按批处理语法标注：

```bat
@echo off
:: 关闭命令回显，只显示脚本自身的输出

setlocal enabledelayedexpansion
:: 启用变量延迟展开：括号代码块内必须用 !var! 才能取到运行时的实时值

set /p net=请输入网段前三位(例如192.168.1):
:: 接收用户输入网段前缀，脚本无需每次改源码

set output=alive_%net%.log
:: 输出文件按网段自动命名，便于多次扫描留档

echo 正在扫描 %net%.1 - %net%.254，结果写入 %output% ...
echo. > %output%
:: 先写入空行/清空旧文件，避免残留上次结果

for /L %%i in (1,1,254) do (
    rem 丢弃全部输出，只依赖退出码：0=通，1=超时/失败
    rem 注意：脚本内循环变量是 %%i（双百分号）
    ping -n 1 -w 200 %net%.%%i >nul 2>&1

    rem errorlevel 为 0 表示该地址存活，追加写入清单
    if !errorlevel! equ 0 (
        echo %net%.%%i 在线 >> %output%
    )
)
echo 扫描完成。
type %output%
:: 展示最终在线设备清单
```

脚本关键设计解读：

| 设计点                                    | 说明                                                         |
| ----------------------------------------- | ------------------------------------------------------------ |
| `set /p`                                  | 交互式接收网段前缀，一个脚本通吃所有 /24 网段                |
| `>nul 2>&1`                               | ping 的正常/错误输出全部丢弃，只看退出码，输出干净           |
| `errorlevel`                              | CMD 中上一条命令的退出码系统变量，ping 成功=0                |
| `enabledelayedexpansion` + `!errorlevel!` | 括号代码块内普通 `%errorlevel%` 在**解析时**被提前展开、拿不到实时值；必须用延迟展开 `!errorlevel!` |
| 括号块内用 `rem` 而非 `::`                | `::` 本质是标签，放在 `( ... )` 代码块内会报「此时不应有 ::」类语法错误；**块内注释一律用 `rem`**，块外两者均可 |

使用建议：临时看一眼用命令行版（§4.2–4.5）；日常工作频繁扫描，务必做成脚本——逻辑清晰、可注释、可复用、可二次加工（如追加 TTL 记录、按网段归档）。

### 4.8 扫描避坑清单

- [ ] **单/双百分号**：CMD 窗口手打用单 `%i`，写入 .bat 必须 `%%i`。批处理解析器遇 `%` 会尝试变量展开，写错直接语法错误或变量被替换为空——这是复制网上命令到脚本时最常见的报错来源。
- [ ] **权限**：扫描本身无需管理员；但后续的 `arp -d`、`route` 修改等需要提升，建议一开始就用管理员窗口跑完整套排查（用 `net session` 验证，见 §1.3）。
- [ ] **生产环境控制强度**：短超时猛扫可能压垮 CPU 能力不足的低端路由器/交换机，严重时全网瘫痪。原则：一次只扫一段、每 IP 一个包、超时设小、并发限量；核心网络/生产环境先评估再动手。
- [ ] **并行 IO 竞争**：并行版每条命令写同一个文件，量大时可能丢行；跨多段扫描建议分批或改用 PowerShell（§9.3）。
- [ ] **不响应 ≠ 离线**：设备可能禁 ICMP（打印机、摄像头常见），ping 不通时用其他方式复核（§8 场景三）。
- [ ] **延迟基准**：内网有线正常延迟 1–5ms；延迟异常先看设备负载再怀疑链路——老旧摄像头被推流时延迟可从 2ms 飙到 100ms+，是设备忙而非线路差。

## 5. Ping 返回信息诊断手册

### 5.1 常见返回信息一览表

| 返回信息                                           | 含义                                               | 常见原因                                                     | 排查动作                                                     |
| -------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Request timed out**（请求超时）                  | 请求已发出，但未在超时时间内收到应答               | ① 对方已关机或网络上不存在该地址 ② 与对方不在同一网段，经路由也找不到对方 ③ 对方存在但设置了 ICMP 过滤（防火墙） ④ 本机网卡 IP 配置错误 | 先 `ping -a 目标IP`：能解析出 NetBIOS 名称 → 对方在线但屏蔽 ICMP；解析不出 → 大概率关机/不存在/不同网段。再用 `nbtstat -A 目标IP` 交叉验证（更可靠），或探测对方业务端口 |
| **Destination host unreachable**（目的主机不可达） | 本机或沿途路由器在路由表中**找不到**去往目标的路由 | ① 与对方不在同一网段且未设置默认网关 ② 网线故障（本地链路不通） | `ipconfig` 核对网关与掩码；`route print` 查看默认路由；检查物理链路 |
| **Bad IP address**                                 | 目标地址格式错误或无法解析                         | IP 书写错误、域名无法被解析                                  | 检查拼写；`nslookup` 验证域名                                |
| **Source quench received**                         | 对方或中途设备拥塞，发来「抑制」报文               | 对方或中转服务器繁忙无法回应                                 | 稍后重试、错峰再测                                           |
| **Unknown host**（不知名主机）                     | 主机名无法被 DNS 服务器解析为 IP                   | DNS 服务器故障、域名书写错误、本机与 DNS 间线路故障          | `nslookup 域名 223.5.5.5` 换公共 DNS 对比，分离「本机 DNS 配置」与「域名本身」问题 |
| **No answer**（无响应）                            | 本机存在通向中心主机的路由，但收不到任何应答信息   | 中心主机未工作；双方网络配置不正确；沿途路由器故障；通信线路故障；中心主机路由选择问题 | `tracert` 分段定位中断点                                     |
| **一般故障 / 传输失败**（补充）                    | 本机协议栈或 ARP 层异常，报文未正常发出            | 本地路由缺失、ARP 异常、VPN/虚拟网卡干扰                     | 重启网卡；`netsh winsock reset`；清 ARP 缓存                 |

### 5.2 「请求超时」vs「目的主机不可达」的本质区别

两者都表现为「ping 不通」，但故障层次完全不同，这是新手最容易混淆的点：

| 对比项     | Request timed out（请求超时）                     | Destination host unreachable（不可达）    |
| ---------- | ------------------------------------------------- | ----------------------------------------- |
| 路由表状态 | 沿途路由器**有**去往目标的路由                    | 路由表**没有**去往目标的路由              |
| 报文去向   | 报文已发出并在转发，目标因关机/防火墙等原因未应答 | 报文根本无法继续转发，被路由器直接回绝    |
| 排查方向   | 目标主机状态、防火墙、目标是否在线                | 本机网关/掩码配置、链路物理状态、沿途路由 |

一句话记忆：**超时=路通了人不在；不可达=连路都没有**。

### 5.3 TTL 详解：跳数计算与系统推测

TTL（Time To Live，生存时间）是防环机制：报文每经过一台路由器 TTL 减 1，减到 0 时路由器丢弃该包并给源头发回 ICMP 超时报文。TTL 初值由**对方操作系统**设定，通常是 2 的幂（可修改）。

**跳数计算公式**：经过的路由器跳数 = 对方系统的 TTL 初始值 − 返回的 TTL 值。

示例：返回 TTL=51 → 推算初始值为 64（2⁶）→ 64 − 51 = **13** 跳（原文「64—54」为笔误）。

**TTL 判系统对照表**（已按现代系统实测值修正原文）：

| 操作系统/设备                      | 默认 TTL | 备注                                  |
| ---------------------------------- | :------: | ------------------------------------- |
| Windows Vista/7/8/10/11（NT 内核） |   128    | ⚠️ 原文「Win7/8=64」有误，实测均为 128 |
| Windows 95/98/ME                   |    32    | 历史系统                              |
| Linux                              |    64    | 主流发行版                            |
| Android                            |    64    |                                       |
| macOS（现代版本）                  |    64    | 旧 MacTCP 时代为 60                   |
| Cisco 及多数网络设备               |   255    | 交换机/路由器常见                     |

实战判读：扫到陌生设备显示 `TTL=64` → 大概率 Linux/安卓设备（可能是 Linux 内核摄像头、路由器等）；`TTL=128` → 大概率 Windows；`TTL=255` → 大概率网络设备。局域网跳数少、TTL 消耗小，初值基本能代表系统类型。

⚠️ 三点注意：① 该判定仅作参考——TTL 初值可被修改（注册表 `DefaultTTL`），对照前需先按上式推算初值，跨网段目标还要扣除已消耗的跳数；② 攻击者同样利用该特征推测目标系统实施针对性攻击，安全敏感主机可自定义 TTL 规避；③ 同一网段内不同批次设备即使系统相同，返回 TTL 也可能因设备固件定制而不同，以实测为准。

## 6. 配套网络排查命令集

### 6.1 arp — IP↔MAC 地址解析表

ARP 协议负责把 IP 地址解析成 MAC 地址；与本机通信过的设备都会在 ARP 缓存中留下映射记录，是排查 IP 冲突、确认设备身份的第一工具。

| 参数                          | 作用                                  | 需管理员 |
| ----------------------------- | ------------------------------------- | :------: |
| `-a [inet_addr] [-N if_addr]` | 显示当前 ARP 缓存（可按 IP/接口过滤） |    否    |
| `-g`                          | 同 `-a`（历史兼容写法）               |    否    |
| `-d [inet_addr]`              | 删除指定或全部缓存条目                |   ⚠️ 是   |
| `-s inet_addr mac`            | 静态绑定 IP 与 MAC                    |   ⚠️ 是   |

适用系统：✅ 全版本 ｜ PowerShell 替代：`Get-NetNeighbor`（Win8+）

```bat
arp -a
:: 查看本机所有接口的 IP-MAC 映射表：接口、Internet 地址、物理地址、类型

ping 192.168.1.50 -n 1
arp -a | findstr "192.168.1.50"
:: 先 ping 再查 ARP：确保缓存中能看到目标条目，再与设备标签/交换机 MAC 表比对

arp -d
:: 清空 ARP 缓存（需管理员窗口），处理 ARP 欺骗/冲突残留后重新学习
```

典型场景：① 怀疑 IP 被抢占 → ping 后查 ARP，MAC 与设备实际不符即为冲突；② ping 第一个包超时、后续恢复且延迟高 → 对端 ARP 缓存过期正在重新解析，此时业务不稳定是必然的。

### 6.2 ipconfig — 本机网络配置查看与刷新

| 参数                         | 作用                                           |     需管理员     |
| ---------------------------- | ---------------------------------------------- | :--------------: |
| （无参数）                   | 显示各网卡基本 IP/掩码/网关                    |        否        |
| `/all`                       | 完整配置：含 MAC、DHCP 启用状态、DNS、租约时间 |        否        |
| `/release [适配器]`          | 释放 IPv4 DHCP 租约（`/release6` 对应 IPv6）   |       建议       |
| `/renew [适配器]`            | 重新申请 IPv4 地址（`/renew6` 对应 IPv6）      |       建议       |
| `/flushdns`                  | 清空 DNS 解析器缓存                            |        否        |
| `/displaydns`                | 查看 DNS 缓存内容                              |        否        |
| `/registerdns`               | 向 DNS 重新注册本机主机名记录                  |       ⚠️ 是       |
| `/showclassid` `/setclassid` | DHCP 类 ID 管理                                | ❌ 现代环境极少用 |

适用系统：✅ 全版本 ｜ PowerShell 替代：`Get-NetIPConfiguration`、`Get-DnsClientCache`、`Clear-DnsClientCache`（Win8+）

```bat
ipconfig /all
:: 重点核对四要素：IP、掩码、网关、DNS；顺带确认「DHCP 已启用」与租约是否正常

ipconfig /release & ipconfig /renew
:: 释放并重新获取地址：DHCP 分配异常/换网段接入后的标准修复动作

ipconfig /flushdns
:: 域名改了解析但本机仍是旧结果时使用；解析验证前先清缓存是良好习惯
```

### 6.3 tracert — 路由路径跟踪

| 参数        | 作用                                              | 默认值   |
| ----------- | ------------------------------------------------- | -------- |
| `-d`        | 不对每跳做反向 DNS 解析（**推荐加**，速度快数倍） | 默认解析 |
| `-h N`      | 最大跳数                                          | 30       |
| `-w N`      | 每跳等待应答的超时毫秒数                          | 4000     |
| `-4` / `-6` | 强制 IPv4 / IPv6                                  | 自动     |

适用系统：✅ 全版本 ｜ PowerShell 替代：`Test-NetConnection 目标 -TraceRoute`（PS 4.0+）

```bat
tracert -d -w 500 www.baidu.com
:: -d 跳过主机名解析提速；从哪一跳开始出现 * * * 即故障边界
```

判读要点：中间某跳连续 `*` 不一定是故障——很多设备禁止响应 TTL 到期报文，只要**后续跳仍正常出现**，说明流量已越过该设备；只有连续多跳全 `*` 且到不了目标，才是真断点。

### 6.4 pathping — 路径跟踪 + 逐跳丢包统计

结合 ping 与 tracert 的优势：先给出路径，再对每一跳统计丢包率与延迟，适合定位「时通时断」「某段丢包」类问题。

| 参数   | 作用                   | 默认值   |
| ------ | ---------------------- | -------- |
| `-n`   | 不解析主机名（提速）   | 默认解析 |
| `-q N` | 每跳发送的探测包数     | 100      |
| `-p N` | 相邻两次探测的间隔毫秒 | 250      |
| `-w N` | 每次应答等待超时毫秒   | 1000     |

适用系统：✅ Vista+（Win10/11 仍内置）；⚠️ 无官方 PowerShell 替代；**默认探测量大、运行慢**（每跳 100 包 × 250ms 间隔），排查时建议收着用：

```bat
pathping -n -q 20 10.0.0.1
:: -n 提速、-q 20 控制探测强度；输出前半段为路径，后半段为逐跳丢包率统计
```

### 6.5 netstat — 连接与端口状态

| 参数       | 作用                                 |     需管理员     |

### 6.6 nslookup — DNS 诊断

```bat
nslookup www.example.com
:: 用本机配置的 DNS 服务器解析，看返回的地址与服务器
```

```bat
:: 查看 IPv4 路由表：0.0.0.0 开头的行即默认路由（默认网关）

:: 快速确认默认路由与跃点数；「不可达主机」故障先看这里
```

## 7. TCP 连接状态与建连/断连过程

### 7.1 TCP 连接全状态表

TCP 连接从建立到释放会经历多个状态，`netstat -ano` 看到的每一行就是一个状态快照。掌握状态含义是分析连接异常的基础：

| 状态                     | 含义                                          | 常见出现方           | 运维关注点                                    |
| ------------------------ | --------------------------------------------- | -------------------- | --------------------------------------------- |
| LISTEN                   | 侦听来自远方的 TCP 端口连接请求               | 服务器               | 服务是否已启动/监听端口是否正确               |
| SYN-SENT                 | 已发送连接请求，等待匹配的连接请求            | 客户端               | 大量出现 = 对端不可达或端口被拦截             |
| SYN-RECEIVED（SYN-RCVD） | 已收到并回发连接请求，等待对方确认            | 服务器               | 大量出现 = 疑似 SYN Flood 攻击                |
| ESTABLISHED              | 连接已建立，可双向传输数据                    | 双方                 | 正常业务连接                                  |
| FIN-WAIT-1               | 等待远程的中断请求，或先前中断请求的确认      | 主动关闭方           | —                                             |
| FIN-WAIT-2               | 等待远程 TCP 的连接中断请求                   | 主动关闭方           | 长期滞留 = 对端迟迟不回 FIN                   |
| CLOSE-WAIT               | 等待本地应用发来连接中断请求                  | 被动关闭方           | 大量滞留 = 本机应用未及时关闭连接（程序缺陷） |
| CLOSING                  | 等待远程对连接中断的确认                      | 双方同时关闭（少见） | —                                             |
| LAST-ACK                 | 等待原发向远程的中断请求的最终确认            | 被动关闭方           | —                                             |
| TIME-WAIT                | 等待足够时间确保远程收到中断确认（持续 2MSL） | 主动关闭方           | 高并发短连接下数量大属正常现象                |
| CLOSED                   | 没有任何连接状态                              | —                    | —                                             |

### 7.2 三次握手（TCP 连接建立）

TCP 连接建立采用客户-服务器模式：主动发起连接的进程叫客户，被动等待连接的进程叫服务器。

|    步骤    | 方向            | 报文标志                                     | 状态迁移                                             |
| :--------: | --------------- | -------------------------------------------- | ---------------------------------------------------- |
| 第一次握手 | 客户端 → 服务器 | `SYN=1, seq=x`（请求建立连接）               | 客户端：CLOSED → SYN-SENT；服务器：LISTEN → SYN-RCVD |
| 第二次握手 | 服务器 → 客户端 | `SYN=1, ACK=1, seq=y, ack=x+1`（同意并确认） | 服务器：SYN-RCVD                                     |
| 第三次握手 | 客户端 → 服务器 | `ACK=1, ack=y+1`（确认）                     | 双方 → ESTABLISHED                                   |

第三次握手后连接建立完成，只要任何一方不发出释放请求，连接将一直保持。

### 7.3 四次挥手（TCP 连接释放）

TCP 连接是**全双工**的，每个方向必须单独关闭：一方完成数据发送后发 FIN 终止本方向连接；收到 FIN 只意味着该方向没有数据流动，另一方仍可发送数据。先关闭的一方执行主动关闭，另一方执行被动关闭。

| 步骤 | 方向            | 报文与说明                                                   |
| :--: | --------------- | ------------------------------------------------------------ |
|  1   | 客户端 → 服务器 | 发送 `FIN`，关闭「客户→服务器」方向的数据传送（FIN 占用一个序号） |
|  2   | 服务器 → 客户端 | 回发 `ACK`，确认序号为收到的序号加 1                         |
|  3   | 服务器 → 客户端 | 服务器关闭该方向连接，发送 `FIN`                             |
|  4   | 客户端 → 服务器 | 回发 `ACK` 确认，序号加 1；客户端进入 TIME-WAIT，等待 2MSL 后 CLOSED |

### 7.4 结合 netstat 的连接异常判读

| 现象                  | 可能原因                                     | 处理方向                                                 |
| --------------------- | -------------------------------------------- | -------------------------------------------------------- |
| 本机大量 `SYN_SENT`   | 对端服务未监听 / 端口被防火墙拦截 / 路由不通 | `Test-NetConnection IP -Port` 验证端口；tracert 验证路径 |
| 服务器大量 `SYN_RCVD` | 疑似 SYN Flood 攻击                          | 启用 SYN Cookie / 上流量清洗 / 封源                      |
| 本机大量 `CLOSE_WAIT` | 本机应用收到关闭请求后未调用 close           | 排查应用代码/重启服务，属程序缺陷                        |
| 本机大量 `TIME_WAIT`  | 短连接高频创建销毁（2MSL 后自动消失）        | 属正常，可开启连接复用（Keep-Alive）缓解                 |
| `ESTABLISHED` 异常多  | 业务正常增长或连接泄漏                       | 结合业务判断，核对进程 PID                               |

## 8. 常见故障排查清单

> 六个高频场景的可勾选操作清单，步骤命令均出自前文章节，可打印张贴或贴入运维 wiki。

### 场景一：电脑突然上不了网

按 §3.4 四步自诊断法由近及远定位：

- [ ] `ping 127.0.0.1` —— 验证协议栈
- [ ] `ping 本机IP` —— 验证网卡与 IP 配置
- [ ] `ping 网关` —— 验证内网链路
- [ ] `ping 223.5.5.5`（公网 IP）—— 验证出口
- [ ] `ping www.baidu.com`（域名）—— 验证 DNS
- [ ] 按卡点定位问题域并处理（协议栈→`netsh winsock reset`；网卡→重装驱动/`ipconfig /renew`；网关→查线路；DNS→`ipconfig /flushdns` 或改公共 DNS）

### 场景二：能 ping 通，但业务连不上（共享/网页/应用）

ping 通只代表 IP 层通，问题在更高层：

- [ ] `ping 目标IP` —— 确认 IP 层通畅
- [ ] `arp -a | findstr 目标IP` —— 记录对方 MAC，与设备实际 MAC 比对，排除 IP 冲突/绑定错误
- [ ] `Test-NetConnection 目标IP -Port 445`（或 `telnet 目标IP 445`）—— 验证业务端口是否开放
- [ ] `netstat -ano` —— 查看本机对应服务是否在监听
- [ ] 核对访问权限/凭据/防火墙规则

根因清单：端口被防火墙拦截、服务未启动、访问权限不足、IP 被绑定错误 MAC。

### 场景三：ping 不通，但设备可能在用

禁 ICMP ≠ 离线（打印机、摄像头、安全设备常见默认禁 ping）：

- [ ] 浏览器访问设备管理页面，或探测其业务端口
- [ ] `ping -a 目标IP` / `nbtstat -A 目标IP` —— 尝试解析主机名，能解析说明在线
- [ ] `arp -a` —— 看缓存中有无该设备 MAC
- [ ] 核对交换机对应端口状态
- [ ] 结论原则：ping 不通时先别断定离线，多手段交叉验证

### 场景四：疑似 IP 冲突

- [ ] `ping 冲突IP` —— 激活链路上的映射
- [ ] `arp -a | findstr 冲突IP` —— 记录解析到的 MAC
- [ ] 与设备标签/交换机 MAC 表比对，不一致即被抢占
- [ ] 临时恢复：`ipconfig /release` + `ipconfig /renew`（DHCP 环境）
- [ ] 长期治理：DHCP 保留地址 / 排查私接设备 / 交换机端口绑定

### 场景五：全网段设备清点（资产盘点）

- [ ] §4.7 批处理脚本扫描，得到 `alive_网段.log` 在线清单
- [ ] 依据返回 TTL 推测设备类型（§5.3 对照表）
- [ ] `arp -a` 交叉核对 IP-MAC 映射
- [ ] 结果粘贴 Excel 分列，建立 IP 台账（备注设备名/责任人/位置）

### 场景六：网络时断时续 / 丢包

- [ ] `ping -t 192.168.1.100` —— 持续观测：网线松动/水晶头接触不良→零星丢包；无线信号差→延迟忽高忽低；带宽被占满→延迟稳定居高
- [ ] `ping -t 192.168.1.100 > ping_log.txt` —— 落盘留证，跑一段时间后 Ctrl+C，用日志回溯
- [ ] 间歇采样（每 3 秒发 2 包）：

```bat
:loop
ping -n 2 192.168.1.100
timeout /t 3 /nobreak >nul
goto loop
```

（`timeout /t 3 /nobreak >nul`：等待 3 秒且不允许按键跳过、不显示倒计时。⚠️ 适用 Vista+，XP 无 timeout 命令。）

- [ ] `pathping -n -q 20 远端目标` —— 逐跳丢包定位（§6.4）
- [ ] 判读：零星丢包→查线缆/水晶头/无线干扰；延迟稳定偏高→查带宽占用；第一个包超时后续恢复→ARP 重新解析（§6.1）

### 9.3 网段扫描的 PowerShell 替代写法

```powershell
# Windows PowerShell 5.1（Win10/11 内置）：串行探测并输出在线 IP
1..254 | ForEach-Object {
    $ip = "192.168.1.$_"
    if (Test-Connection -ComputerName $ip -Count 1 -Quiet) { $ip }
}
# 逐段注释：1..254 生成 1 到 254 的数字序列 → 逐个拼出 IP →
# -Count 1 单包探测、-Quiet 只返回布尔值 → 在线则输出该 IP

# PowerShell 7+（需另装）：并行扫描，-ThrottleLimit 限制并发防止压垮网络
1..254 | ForEach-Object -Parallel {
    $ip = "192.168.1.$_"
    if (Test-Connection -TargetName $ip -Count 1 -Quiet) { $ip }
} -ThrottleLimit 50
# 注意：-Parallel 与 -TargetName 仅 PS 7+ 支持
```

⚠️ 并发提醒：与 §4.8 相同，并发过高同样会冲击老旧网络设备，`-ThrottleLimit` 建议不超过 50，生产环境更低。

## 10. 附录

### 10.1 IPv6 地址压缩规则（已修正原文示例）

IPv6 使用冒号十六进制表示：128 位地址每 16 位分成一段，每段用十六进制表示、冒号分隔。完整写法：

```text
2001:0D12:0000:0000:02AA:0987:FE29:9871
```

两级压缩规则：

1. **每段的前导零可省略**：`0D12→D12`、`02AA→2AA`、`0987→987`，得
   `2001:D12:0:0:2AA:987:FE29:9871`（原文此处漏写冒号致误读，已修正）
2. **连续的全零段可用双冒号 `::` 代替**：
   `2001:D12::2AA:987:FE29:9871` —— ⚠️ **双冒号在一个地址中只能出现一次**，出现多次时无法确定每段省略了几个零。

再例：`FE80:0:0:0:FF:3BA:891:67C2` → `FE80::FF:3BA:891:67C2`（原文将 FF80/FE80 混写，已按链路本地地址前缀 FE80 统一；`FE80::/10` 为链路本地地址段）。

### 10.2 网段扫描耗时速算

串行扫描最坏耗时 ≈ 空地址数量 × 单次超时。/24 网段对比：

| 参数组合              | 254 地址（约半数空）耗时估算 | 适用          |
| --------------------- | ---------------------------- | ------------- |
| 默认（4 包 × 4000ms） | ≈ 8.5 分钟以上               | 仅单点测试    |
| `-n 1 -w 200` 串行    | ≈ 51 秒                      | 日常单网段    |
| `-n 1 -w 200` 并行    | 数秒至十几秒                 | 多网段/大范围 |

### 10.3 经验要点汇总

- **单 % 双 % 法则**：CMD 窗口手打单 `%i`，批处理文件内双 `%%i`——for 循环能不能跑起来的第一判据。
- **权限自检**：`net session` 报「拒绝访问」即当前窗口无管理员权限，改用管理员终端再执行提升类操作。
- **延迟基准**：内网有线正常 1–5ms；异常延迟先看设备负载（摄像头推流时 2ms→100ms+ 属设备忙）再查链路。
- **生产扫描守则**：单包、短超时、一次一段、限并发；低端路由器可被并发 ICMP 压垮。
- **排查链路**：ping 验存活 → arp 核 MAC → `Test-NetConnection`/telnet 验端口 → 登设备管理面定位——四步走完，局域网问题基本定位到七七八八。
- **命令组合**：`ipconfig`（配置）+ `tracert`（路径）+ `pathping`（丢包）三件套可应对绝大多数日常网络故障。

| 术语     | 全称/含义                                                    |
| -------- | ------------------------------------------------------------ |
| ICMP     | Internet 控制报文协议，ping 的底层协议                       |
| TTL      | 生存时间，防环计数器，每过一台路由器减 1                     |
| ARP      | 地址解析协议，把 IP 解析为 MAC                               |
| NetBIOS  | 传统主机名服务，`nbtstat -A` 可按 IP 查询名称                |
| MTU / DF | 最大传输单元 / 不分段标志，`ping -f -l` 配合探测路径 MTU     |
| DHCP     | 动态主机配置协议，自动分配 IP 地址                           |
